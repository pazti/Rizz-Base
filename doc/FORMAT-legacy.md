# V1 project format and Go API

## Terms

| Database concept | Rizzbase name | V1 representation |
| --- | --- | --- |
| Database | Project | One encrypted `.rizz` file |
| Collection | Lobby | Named, generated-ID group in a Project |
| Document | Yap | JSON value stored under a caller-supplied ID |
| Field | Field | Any value supported by JSON |

## Encrypted file envelope

The file is UTF-8 text: pairs of lowercase words from the fixed 16-word V1
vocabulary encode each byte of the binary envelope. The binary envelope contains
a versioned 8-byte identifier, a random 16-byte salt, a random 12-byte nonce,
and AES-256-GCM ciphertext plus its authentication tag. The complete header is
authenticated as additional data. The project metadata and all Lobby/Yap data
are encrypted; the version identifier, salt, nonce, and encoded file size are
public.

The encryption key is derived from the caller's nonempty passphrase using
PBKDF2-HMAC-SHA256 with 600,000 iterations and a 32-byte output. Every project
write uses fresh random salt and nonce values. The Brainrot words only encode
data; they do not provide security.

V1 reads the entire file into memory and limits the encoded text to 64 MiB.
There is no passphrase recovery or WAL. A passphrase can be rotated only while
the current passphrase is known, by exporting and restoring a plaintext JSON
backup into a new encrypted Project; this is not an in-place key change.
Protect the backup as sensitive data. A wrong
passphrase and authenticated-data corruption return the same authentication
error. Keep a strong passphrase and separate backups.

## Go API

Module: `rizzbase/engine`, in the `engine/` directory.

- `core.CreateProject(path, name, passphrase) (*Project, error)`
- `core.OpenProject(path, passphrase) (*Project, error)`
- `core.ImportProject(path, passphrase, backupPath) (*Project, error)`
- `core.CreateLobby(path, passphrase, name) (Lobby, error)`
- `core.ListLobbies(path, passphrase) ([]Lobby, error)`
- `core.DeleteLobby(path, passphrase, lobbyID) error`
- `core.CreateYap(path, passphrase, lobbyID, yapID string, value any) error`
- `core.GetYap(path, passphrase, lobbyID, yapID string) (json.RawMessage, error)`
- `core.ListYaps(path, passphrase, lobbyID string) ([]Yap, error)`
- `core.UpdateYap(path, passphrase, lobbyID, yapID string, value any) error`
- `core.DeleteYap(path, passphrase, lobbyID, yapID string) error`
- `core.QueryYaps(path, passphrase, lobbyID string, options QueryOptions) ([]Yap, error)`

`QueryOptions` contains `Where []Filter`, an optional `OrderBy *OrderBy`, and
an optional `Limit *int`. Each filter has a dot-separated `Field`, one of
`==`, `!=`, `>`, `>=`, `<`, `<=` as `Operator`, and a JSON `Value`. Filters are
AND-combined. Nested paths traverse JSON objects; missing fields do not match.
Equality compares JSON values, including objects and arrays. Filter comparison
operators compare numbers or strings of matching types only. An order-by
direction is `asc` or `desc`; numbers sort before strings, and missing or
unsupported values sort last. Ties fall back to Yap-ID order. Filtering,
ordering and then limiting happen in that order. The implementation decrypts
and scans the whole Lobby in memory.

IDs are 1–128 bytes. Lobby IDs are generated by `CreateLobby`; Yap IDs are
provided by the caller. Lobby and Yap list results are sorted by ID. Updating or
deleting a missing record returns a typed `core` error; duplicate Yap creation
also returns a typed error. Deleting a Lobby deletes its contained Yaps as part
of the same atomic project update.

## CLI JSON protocol

The `engine/cmd/rizzbase` executable reads one JSON object from stdin and writes
one JSON object to stdout. It processes one operation per process. Every request
requires `operation`, `path`, and `passphrase`; `create`/`lobby.create` also
require `name`; Yap operations use `lobbyId`, `yapId`, and `data` as appropriate.
The `project.import` operation accepts a `backupPath` containing a validated
decrypted JSON Project and creates a new encrypted file without overwriting an
existing one. The `yap.query` operation also accepts `lobbyId` and a `query`
object with `where`, `orderBy`, and `limit`, and returns matching records in
`yaps`.
Success has `ok: true` and the relevant result key (`project`, `lobby`,
`lobbies`, `yap`, `yaps`, or `data`). Failure has `ok: false` and `error`, and
returns a nonzero process status. Passphrases must travel through a private
stdin stream, never command arguments.

## Disk safety

Project modifications use an adjacent lock directory to serialize cooperating
writers within one local filesystem. A present lock blocks writes. If a process
crashes, its lock directory may need manual cleanup after verifying that no
writer is active. New bytes are fully written and synced before atomic rename;
the previous file remains intact until publication. Cross-process locking over
network filesystems and recovery on filesystems without atomic same-directory
rename are not supported.
